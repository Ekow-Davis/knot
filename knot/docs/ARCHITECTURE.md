# Knot — architecture

Project Wonder Woman. A private question game for two people, shipped as an installable PWA.
Home-screen label **W.W.**, served at `ww.forgottenguardian.com`. Inside, the app is called **Knot**.

---

## 1. Shape of the system

```
┌──────────── iPhone / browser ────────────┐        ┌──────────── Railway (one service) ─────────────┐
│ Vue 3 + TS PWA                           │        │ FastAPI                                         │
│  • landing page (browser)                │ HTTPS  │  • /api/*    REST (auth, settings, rounds)       │
│  • app (standalone / home screen)        │◄──────►│  • /api/ws   WebSocket (live sync)               │
│  • WebCrypto: encrypt/decrypt answers    │  WSS   │  • /*        built PWA files + SPA fallback      │
│  • passphrase key kept in IndexedDB      │        │  • purge job (expired rounds/codes/sessions)    │
└──────────────────────────────────────────┘        │ Postgres (Railway plugin)                       │
                                                    │ Resend (6-digit codes) · Web Push (VAPID)       │
                                                    └─────────────────────────────────────────────────┘
```

**One Railway service** builds the frontend and serves it from FastAPI. Reasons:
- It's cheaper than two services.
- Same origin means the session can live in an `httpOnly` cookie, which JavaScript can't read. That's safer than a token in localStorage, and it means no CORS.
- The WebSocket gets the same cookie for free.

In development, Vite runs on :5173 and proxies `/api` to FastAPI on :8000.

| Layer | Choice |

## 3. Accounts, sign-in and pairing

There are exactly two people, and nobody else can get in.

**Sign-in (every time):**
1. Email field → `POST /api/auth/code`. This always answers "if that address can sign in, a code is on its way", whether or not the email is known.
2. 6-digit code → `POST /api/auth/verify`.
   - Codes are stored as an **HMAC-SHA256 with a server secret**, never as plain text.
   - Each code expires after 10 minutes, allows 5 attempts, and can be used once.
   - A new code can't be requested more often than once every 60 seconds per email.
3. If the email belongs to an existing user, the server creates a session (an opaque random token, stored hashed, in an `httpOnly; Secure; SameSite=Lax` cookie, valid 90 days and renewed on use).

**First-time setup.** When the email is verified but has no account yet, the server returns a short-lived signed *verified-email ticket* (15 minutes). There are two paths:
- **Owner (Baron).** If the email matches the `OWNER_EMAIL` env var and no pair exists yet, the ticket alone creates the owner account and the pair.
- **Partner.** The ticket plus a valid **pairing code** creates her account and fills the second seat. From then on, registration is closed permanently.

The final step for both is "What should they call you?", which sets the display name. It can be changed later in settings.

**Pairing codes:**
- Generated by the owner from Settings → Invite. The format is `TIE-XXXX`, avoiding look-alike characters (0/O, 1/I).
- Only an HMAC of the code is stored. A code is single-use and expires after 7 days.
- Generating a new code cancels any older unused one.
- Once the second seat is filled, any further pairing attempt gets "This pair is already complete."

The database enforces the two-person limit: there is a single `pair` row (`id = 1` constraint) with `owner_id` and `partner_id` columns.

## 4. The knot (passphrase and encryption)

The server never sees the passphrase or any answer in readable form.

- **Key derivation:**
  - `Argon2id(passphrase, salt)` with m = 64 MiB, t = 3, p = 1, producing 32 bytes. These settings are deliberately slow, which is what makes a short phrase safe enough.
  - The result is imported as a **non-extractable** AES-GCM key.
  - The salt and parameters are stored on the `pair` row, so both phones derive the same key.
  - The hint text suggests "three or four words you both know"; the minimum is 6 characters.
- **Key check** (catches mismatched phrases):
  - When the knot is first tied, the client encrypts a fixed string and stores the ciphertext and nonce on `pair`.
  - On unlock, the client decrypts it. If that fails, it shows "That's not the phrase you two tied."
- **Remember on this phone:** the non-extractable `CryptoKey` is stored in IndexedDB. The browser keeps the key itself, so even the app's own code can't export the raw bytes.
- **The eye icon** on the phrase field shows or hides the phrase so you can check it.
- **Answers:**
  - Each answer is encrypted with AES-GCM and a fresh 12-byte nonce, then sent as ciphertext.
  - The round ID and author ID are included as associated data, so a sealed answer can't be moved to a different round.
- **Retie (change phrase):**
  - Generates a new salt and a new check value, and bumps `key_version`.
  - Any answers still sealed under the old key can no longer be opened, so they're discarded.
  - The other phone is told to re-enter the new phrase.

## 5. Rounds: nothing is kept

```
draw ──► open (both answer / pass) ──► both sealed ──► both hold ──► revealed ──► [guess: verdict] ──► deleted
                 │                                                                     ▲
                 └──── 24h without reveal ──► expired ──► deleted ─────────────────────┘
```

- `rounds` holds the live round: question, who drew it, who's being guessed about, state and expiry.
- `sealed_answers` holds the ciphertext for each person in that round.
- When the reveal completes (and the verdict, for a Guess), **the round and its answers are deleted**. The only thing kept is the question ID, in `drawn_questions`, so that question isn't drawn again.
- A purge job runs every 10 minutes. It deletes rounds older than 24 hours, expired codes, invites and sessions.
- A **pass** is just a state on the round. The other person sees "[name] passed on that one."
- **Reveal:** both people hold, and the server coordinates it over the WebSocket. The reveal fires when both halves of the ring fill. A tap alternative sends the same signal.
- **Guess verdict:** the person being guessed about answers "Close enough?". The verdict only drives the animation and isn't stored.

## 6. Shared settings and live sync

- **On `pair.settings` (shared, live):** depth, selected categories, Random on/off, and the excluded categories.
  - Every change is broadcast over the WebSocket together with who made it, which drives the "Jules changed depth to Deep" note.
- **On `users`:** each person's Spicy switch. Spicy only enters the draw when **both** have it on.
- **Turn-taking** lives on `pair.turn_user_id`.
- **WebSocket events:** `presence`, `settings`, `turn`, `round.drawn`, `round.sealed`, `round.passed`, `hold.start`, `hold.end`, `round.revealed`, `round.verdict`, `tug`.
- **Offline partner:** "Leave a sealed question" creates the round and your sealed answer, then sends the partner a push notification. It expires after 24 hours like any other round.

## 7. Question bank

Baron never sees the questions.

- **Packs** are JSON files named by ID, for example `silly-002`. Each question has a **permanent ID**, a `type` (`guess`, `both`, `wyr`, `self`), a `depth` (`light`, `medium`, `deep`), a `category`, and its text (plus options for Would You Rather).
- **Encryption:** the pack file is encrypted with `BANK_KEY` (AES-GCM; the key is a Railway env var).
  - The import script reads the file, stores each question's text as its **own encrypted blob**, and prints only counts by category and depth, never any text.
  - The type, depth and category stay readable so the server can filter on them.
- **Merging:** importing a pack merges into the one shared pool by question ID.
  - Re-importing the same pack (same checksum) does nothing.
  - A new pack in an existing category just adds to it, and nothing already played comes back.
- **Draw:** the server picks a random question that matches the shared settings and the Spicy rule, isn't in `drawn_questions`, and isn't retired. It decrypts that one question and sends it to both phones.
- **Retire:** a button on each card sets `retired_at`, and the question never appears again.
- **Content guide:**
  - Ghana / West Africa context; no US/UK-only brands or experiences.
  - Questions about the past assume a relationship that started in senior high. "When we were younger" means then, not childhood.
  - Spicy stays tasteful and only appears under both-on consent.
  - Starting size is about 1,500 questions across all categories and depths.

## 8. Data model

| Table | Purpose |
|---|---|
| `users` | id, email (lower-case, unique), display_name, spicy_on, theme (json: mode, preset, base and accent hue) |
| `pair` | single row: owner_id, partner_id, KDF salt and params, key check and nonce, key_version, settings (json), settings_updated_by/at, turn_user_id |
| `email_codes` | email, code_hmac, attempts, expires_at, consumed_at |
| `sessions` | user_id, token_hash, expires_at, last_used_at, user_agent |
| `invites` | code_hmac, created_by, expires_at, used_at, used_by |
| `question_packs` | id (e.g. `silly-002`), version, checksum, question_count, imported_at |
| `questions` | id, pack_id, type, depth, category, payload + nonce (encrypted), retired_at |
| `drawn_questions` | question_id, drawn_at: the "already played" list, with no answers |
| `rounds` | question_id, drawn_by, subject_id, state, passed_by, created_at, expires_at |
| `sealed_answers` | round_id + user_id, ciphertext, nonce, key_version |
| `push_subscriptions` | user_id, endpoint, p256dh, auth |
