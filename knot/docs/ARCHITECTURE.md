# Knot — architecture

Project Wonder Woman. A private question game for two people, shipped as an installable PWA.
Home-screen label **W.W.**, served at `ww.forgottenguardian.com`. Inside, the app is called **Knot**.

---

## 1. Shape of the system

```
┌──────────── iPhone / browser ────────────┐        ┌──────────── Railway (one service) ─────────────┐
│ Vue 3 + TS PWA                           │        │ FastAPI                                         │
│  • landing page (browser)                │ HTTPS  │  • /api/*    REST (auth, settings, rounds)       │
│  • app (standalone / home screen)        │◄──────►│  • /api/ws   WebSocket (live sync)               │
│  • WebCrypto: encrypt/decrypt answers    │  WSS   │  • /*        built PWA files + SPA fallback      │
│  • passphrase key kept in IndexedDB      │        │  • purge job (expired rounds/codes/sessions)    │
└──────────────────────────────────────────┘        │ Postgres (Railway plugin)                       │
                                                    │ Resend (6-digit codes) · Web Push (VAPID)       │
                                                    └─────────────────────────────────────────────────┘
```

**One Railway service** builds the frontend and serves it from FastAPI. Reasons:
- It's cheaper than two services.
- Same origin means the session can live in an `httpOnly` cookie, which JavaScript can't read. That's safer than a token in localStorage, and it means no CORS.
- The WebSocket gets the same cookie for free.

In development, Vite runs on :5173 and proxies `/api` to FastAPI on :8000.

## 2. Stack

| Layer | Choice |
|---|---|
| Frontend | Vue 3, TypeScript, Vite, `vite-plugin-pwa`, Pinia, Vue Router, `lucide-vue-next` |
| Crypto (client) | WebCrypto AES-GCM-256; `hash-wasm` for Argon2id |
| Backend | FastAPI, SQLAlchemy 2 (async) + asyncpg, Alembic, pydantic-settings |

## 3. Accounts, sign-in and pairing

There are exactly two people, and nobody else can get in.

**Sign-in (every time):**
1. Email field → `POST /api/auth/code`. This always gives the same answer, whether or not the email is known.
   - An email is actually sent only when that address could get in: an existing account, `OWNER_EMAIL` before the pair exists, or anyone while an unused pairing code is open.
   - Sending happens after the response, so response timing doesn't give it away either.
   - Without `RESEND_API_KEY` in development, the code is printed to the uvicorn console instead.
2. 6-digit code → `POST /api/auth/verify`.
   - Codes are stored as an **HMAC-SHA256 with a server secret**, never as plain text.
   - Each code expires after 10 minutes, allows 5 attempts, and can be used once.
   - A new code can't be requested more often than once every 60 seconds per email.
3. If the email belongs to an existing user, the server creates a session (an opaque random token, stored hashed, in an `httpOnly; Secure; SameSite=Lax` cookie, valid 90 days and renewed on use).

**First-time setup.** When the email is verified but has no account yet, the server returns a short-lived signed *verified-email ticket* (15 minutes). There are two paths:
- **Owner (Baron).** If the email matches the `OWNER_EMAIL` env var and no pair exists yet, the ticket alone creates the owner account and the pair.
- **Partner.** The ticket plus a valid **pairing code** creates her account and fills the second seat. From then on, registration is closed permanently.

The final step for both is "What should they call you?", which sets the display name. It can be changed later in settings.

**Pairing codes:**
- Generated by the owner from Settings → Invite. The format is `TIE-XXXXX` (5 characters from a 31-letter alphabet with no 0/O/1/I/L).
  - Typing is forgiving: case, spaces and a missing `TIE-` prefix don't matter.
- Only an HMAC of the code is stored, so it's shown exactly once, at creation.
- A code is single-use and expires after 7 days. Generating a new code cancels any older unused one, and the owner can cancel a code outright.
- **Guess limits:** 5 tries per verified-email ticket and 20 per IP address per hour.
- **Endpoints:** `POST /api/auth/check-invite` lets the pairing screen reject a bad code before asking for a name. `POST /api/auth/join` creates the account.
- Once the second seat is filled, any further pairing attempt gets "This pair is already complete."

The database enforces the two-person limit: there is a single `pair` row (`id = 1` constraint) with `owner_id` and `partner_id` columns.

## 4. The knot (passphrase and encryption)

The server never sees the passphrase or any answer in readable form.

- **Key derivation:**
  - `Argon2id(passphrase, salt)` with m = 64 MiB, t = 3, p = 1, producing 32 bytes. These settings are deliberately slow, which is what makes a short phrase safe enough.
  - The result is imported as a **non-extractable** AES-GCM key.
  - The salt and parameters are stored on the `pair` row, so both phones derive the same key.
  - The hint text suggests "three or four words you both know"; the minimum is 6 characters.
  - Before hashing, the phrase is normalised: Unicode NFKC, curly quotes and dashes straightened, spaces collapsed, lower-cased. iOS capitalising the first letter, or using smart apostrophes, can't make two phones disagree.
  - Argon2id runs in a Web Worker (hash-wasm) so the animation stays smooth during the ~1 second it takes.
  - **Who ties first:** whoever reaches the screen first ties the knot. If both race, the second phone gets `409 already_tied` along with the existing knot, and switches to "enter the phrase".
- **Key check** (catches mismatched phrases):
  - When the knot is first tied, the client encrypts a fixed string and stores the ciphertext and nonce on `pair`.
  - On unlock, the client decrypts it. If that fails, it shows "That's not the phrase you two tied."
- **Remember on this phone:** the non-extractable `CryptoKey` is stored in IndexedDB. The browser keeps the key itself, so even the app's own code can't export the raw bytes.
- **The eye icon** on the phrase field shows or hides the phrase so you can check it.
- **Answers:**
  - Each answer is encrypted with AES-GCM and a fresh 12-byte nonce, then sent as ciphertext.
  - The round ID and author ID are included as associated data, so a sealed answer can't be moved to a different round.
- **Retie (change phrase):**
  - Generates a new salt and a new check value, and bumps `key_version`.
  - Any answers still sealed under the old key can no longer be opened, so they're discarded.
  - The other phone is told to re-enter the new phrase.

## 5. Rounds: nothing is kept

```
draw ──► open (both answer / pass) ──► both sealed ──► both hold ──► revealed ──► [guess: verdict] ──► deleted
                 │                                                                     ▲
                 └──── 24h without reveal ──► expired ──► deleted ─────────────────────┘
```

- `rounds` holds the live round: question, who drew it, who's being guessed about, state and expiry.
- `sealed_answers` holds the ciphertext for each person in that round.
- When the reveal completes (and the verdict, for a Guess), **the round and its answers are deleted**. The only thing kept is the question ID, in `drawn_questions`, so that question isn't drawn again.
- A purge job runs every 10 minutes. It deletes rounds older than 24 hours, expired codes, invites and sessions.
- **Who answers:** Guess (the drawer guesses, the other person writes the truth), Both and Would You Rather → both answer. "Just you" → only the drawer writes; the other person reads.
- **A pass** deletes the round straight away, along with anything already sealed, unread. The other person sees "[name] passed on that one." **"Never show this one again"** also retires the question permanently.
- **Revealing ("pulling your end"):**
  - Hold the knot for 1.2 seconds, or use the tap alternative, to pull your end. It stays pulled, so there's no need to keep holding.
  - **Both pulled:** both phones get the answers, then the round and its answers are deleted.
  - **The other person is away:** you can read it now, and the round waits for their pull or the 24-hour expiry.
  - **They're here but haven't pulled after 15 seconds:** "Read it now" appears.
  - The ring filling is shown live to the other phone (`round.hold`), but only as animation.
- **Guess verdict:** an automatic match if the guess and the truth share a meaningful word. Otherwise the person who was guessed about decides "Close enough?". It's broadcast, never stored.
- **Starting a card when you're both here: "I'm ready".**
  - Each person taps ready (`POST /api/rounds/ready`), and the other phone sees "Ama is ready." Ready can be taken back.
  - When both are ready, the server deals one card to both phones at once (`round.drawn` to both).
  - Ready lives in memory only, and closing the app clears it.
  - Drawing alone (`POST /api/rounds`) is refused with `use_ready` while both are online.
- **One person away:** whoever is on draws directly. That's "leave a sealed question".
- **Where each person is:** each phone tells the other which screen it's on (a `where` message on the socket; information only, not stored). The game screen can then say "Ama went back to the home screen" or show mix changes ("Ama changed depth to Deep"), and Home can say "Ama is still at the table".
- **Empty hat:** "Shuffle them back in" reshuffles and counts as ready. The other phone sees "Baron shuffled them back in" and one tap deals.
- **The "drawer" alternates behind the scenes** (`pair.turn_user_id`) after each reveal or pass. It only decides who guesses on a Guess card and who writes on a "Just you" card; nobody sees it as a turn.
- **The flow when you're both here:** the reveal screen itself carries "Ready for the next one" (or swipe left) and "That's enough for tonight". There is no in-between screen: the answers stay up until the next card is dealt, then give way to it. Ending shows "Twelve knots tied.", with the count kept on the phone for that evening only.
- **Together, one card at a time;** apart, a queue. While the other person is away you can leave up to 12 sealed questions (migration 0003 dropped the one-round index). Each phone's `/rounds/current` is the oldest card waiting on *you* (answer or pull), else the newest you're waiting on them for.
- **Reading alone** adds you to `rounds.read_by`: the card drops off your phone so you can carry on, and stays until they pull or it expires.
- **Push only when they can't see it:** the app reports `away`/`back` over the socket when it leaves the screen, and notifications go to anyone not connected *or* in the background (`hub.reachable`). The game itself still counts a backgrounded person as here.

## 6. Shared settings and live sync

- **On `pair.settings` (shared, live):** depth, selected categories, Random on/off, and the excluded categories.
  - Every change is broadcast over the WebSocket together with who made it, which drives the "Jules changed depth to Deep" note.
- **On `users`:** each person's Spicy switch. Spicy only enters the draw when **both** have it on.
- **Turn-taking** lives on `pair.turn_user_id`.
- **How live updates work:** every change goes through a normal REST endpoint (`PATCH /api/settings`, `PUT /api/me/spicy`, `PATCH /api/me`, `POST/PUT /api/knot`). After it commits, the server pushes the new state to both phones over `/api/ws`. The socket only carries server-to-phone events plus a keep-alive ping.
  - **Sign-in on the socket:** the same session cookie. A connection without a valid session closes with code 4401, which the app treats as "signed out".
  - **Reconnecting:** iOS kills sockets in the background, so the app reconnects when it returns to the foreground, when the network comes back, or with backoff from 1 to 30 seconds. Each connection starts with `hello`, and the app re-fetches `/api/home` on it.
- **WebSocket events:**
  - Pair and settings: `hello` (with `partner_online`, `partner_ready`, `partner_where`), `presence`, `settings`, `spicy`, `profile` (name and theme), `knot` (tied or retied), `pair` (she joined).
  - Game: `ready`, `where`, `round.drawn`, `round.empty`, `round.reshuffled`, `round.sealed`, `round.hold`, `round.pull`, `round.revealed`, `round.passed`, `round.verdict`, `round.expired`, `tug`.
- **The hat rule** is shared by the server (`api/app/mix.py`) and the app (`stores/home.ts`):
  - **Normal mode:** exactly the chosen categories.
  - **Random mode:** everything except the excluded categories.
  - **Spicy is never a hat category.** It's in play only when both personal switches are on.
  - The hat can't be emptied in either mode.
- **Theme:** stored on the account (`users.theme`) and cached on the phone. Deep dims the palette on home and game screens only.
- **Offline partner:** "Leave a sealed question" creates the round and your sealed answer, then sends the partner a push notification. It expires after 24 hours like any other round.
- **Push notifications (Session 7):**
  - Opt-in screen (`NotifyView`) shown once after unlocking, plus a toggle in Settings. Signing out removes this phone's subscription.
  - Server: `GET /api/push/key` (503 `push_off` until VAPID is set), `POST /api/push/subscribe` (https endpoints only, upsert), `POST /api/push/unsubscribe`. Sending uses `pywebpush` in a thread with a 24-hour TTL; endpoints that answer 404/410 are deleted.
  - **Only when the partner is not in the app** (no live socket): a sealed question left for them, their sealed question answered ("your end of the rope is waiting"), and a tug. Nothing is sent while both are online.
  - Notification text never contains a question or an answer: just a display name and a fixed line. Tapping opens `/play`.
  - `public/push-sw.js` is pulled into the generated service worker with `workbox.importScripts`.

## 7. Question bank

Baron never sees the questions.

- **Packs** are JSON files named by ID, for example `silly-002`. Each question has a **permanent ID**, a `type` (`guess`, `both`, `wyr`, `self`), a `depth` (`light`, `medium`, `deep`), a `category`, and its text (plus options for Would You Rather).
- **Encryption in transit:** packs reach Baron already sealed (`KNOTPACK1` + nonce + AES-GCM ciphertext) with a separate **transport key** in `transport.key`. `import_pack --key-file packs/transport.key` opens them in memory only.
- **Encryption at rest:** `BANK_KEY` (AES-GCM; a Railway env var), with each question's ID as associated data.
  - The import script reads the file, stores each question's text as its **own encrypted blob**, and prints only counts by category and depth, never any text.
  - The type, depth and category stay readable so the server can filter on them.
- **Merging:** importing a pack merges into the one shared pool by question ID.
  - Re-importing the same pack (same checksum) does nothing.
  - A new pack in an existing category just adds to it, and nothing already played comes back.
- **Draw:** the server picks a random question that matches the shared settings and the Spicy rule, isn't in `drawn_questions`, and isn't retired. It decrypts that one question and sends it to both phones.
- **Retire:** a button on each card sets `retired_at`, and the question never appears again.
- **Content guide:**
  - Ghana / West Africa context; no US/UK-only brands or experiences.
  - Questions about the past assume a relationship that started in senior high. "When we were younger" means then, not childhood.
  - Spicy stays tasteful and only appears under both-on consent. It never assumes physical history: attraction, anticipation, firsts, flirting, and what each would like.
  - Full rules: `docs/QUESTION-GUIDE.md` (rules only, no questions).
  - **First bank (Session 7):** 1,435 questions in seven `-001` packs, weighted toward Silly, Big and Cozy. The throwaway `test-000` pack is removed with `import_pack --remove test-000`.

## 8. Data model

| Table | Purpose |
|---|---|
| `users` | id, email (lower-case, unique), display_name, spicy_on, theme (json: mode, preset, base and accent hue) |
| `pair` | single row: owner_id, partner_id, KDF salt and params, key check and nonce, key_version, settings (json), settings_updated_by/at, turn_user_id |
| `email_codes` | email, code_hmac, attempts, expires_at, consumed_at |
| `sessions` | user_id, token_hash, expires_at, last_used_at, user_agent |
| `invites` | code_hmac, created_by, expires_at, used_at, used_by |
| `question_packs` | id (e.g. `silly-002`), version, checksum, question_count, imported_at |
| `questions` | id, pack_id, type, depth, category, payload + nonce (encrypted), retired_at |
| `drawn_questions` | question_id, drawn_at: the "already played" list, with no answers |
| `rounds` | question_id, drawn_by, subject_id, state, passed_by, created_at, expires_at |
| `sealed_answers` | round_id + user_id, ciphertext, nonce, key_version |
| `push_subscriptions` | user_id, endpoint, p256dh, auth |

- **Link preview (Open Graph):** blue background with Baron's emblem, captioned "A project series to the one I love". Plus `noindex`.
- **Code email:**
  - From: "no-reply" at `no-reply@forgottenguardian.com`.
  - Subject: `Your code: 482913`.
  - Body: just the code and how long it lasts.
- **Inside the app** everything is Knot, with no DC names. The default palette is Plum, not gold on blue.
- **Icons and the link-preview card** all come from one file, `web/brand/emblem.png`, via `npm run make:brand`. The emblem is trimmed to its edges first so it fills the space.
  - **Favicons (32 and 180):** just the emblem, transparent.
  - **App icons:** an opaque emblem fills the icon edge to edge; a transparent one sits at 86% on deep blue (`--bg` to change it). The iPhone icon has no transparency, and the Android maskable icon keeps the emblem at 70% inside the safe circle.
- **Landing page install steps** adapt to the browser:
  - **iOS 26 Safari:** ••• → Share → Add to Home Screen (with "Open as Web App" on). Safari 26 freezes the OS version at 18_6, so detection uses `Version/26`.
  - **Older iOS:** Share in the toolbar. **iPad:** Share at the top.
  - **Chrome or Firefox on iOS:** their own Share menu.
  - **Android:** a real Install button via `beforeinstallprompt`.
  - **In-app browsers** (Instagram, WhatsApp, Snapchat, Facebook, TikTok…): "Open this in Safari first", with app-specific directions.
  - **Desktop:** "open it on your phone".
  - "Just open it here" uses it in the browser tab, without notifications on iPhone.
